Shadow

Published on March 2026

Solution

Entry point for the challenge is the public-facing repository https://github.com/CommitDust-oss

At first glance, the repository looks like a simple utility project, nothing suspicious. However, deeper inspection into its past reveals traces of a deleted fork that once contained sensitive AWS credentials embedded in a commit.

The mission is to recover those credentials and use them to retrieve the flag from an AWS S3 bucket.

Step 1: Finding the Breadcrumb

Players look around the Github user and find a repo named Bucket-World. Further, they can find a comment in a PR in that repo at https://github.com/CommitDust-oss/Bucket-World/pull/1

Here the short sha commit is exposed: "Additionally, double check if 471f993 from my fork of ember-cli-deploy-s3 is gone or not!"

The players can also go to the gist https://gist.github.com/CommitDust-oss which mention the s3 bucket name that needs to be used later.

This hint suggests that an earlier fork once had a commit that was later deleted or force-pushed away. Even though the fork was removed, GitHub's backend may still store the underlying Git objects.

Step 2: Retrieving the Deleted Commit

Players can go to the ember-cli-deploy github profile and within the ember-cli-deploy-s3 repo, they can look for the commit like:

https://github.com/ember-cli-deploy/ember-cli-deploy-s3/commit/471f993

This shows a file containing base64 content holds encoded AWS data.

Step 3: Extracting the Blob Content

Once decoded, these represent AWS Access Keys and Secret Keys for a temporary IAM user or role.

{
  "type": "ctf-temp-role",
  "role_arn": "arn:aws:iam::972918601805:role/ctf-github-leak-role",
  "external_id": "githubShadow",
  "aws_region": "us-west-2",
  "hint": "buckets are cool"
}

Step 4: Assume the IAM role

Now that you have the role_arn and external_id, use aws sts assume-role to get temporary credentials.

aws sts assume-role --role-arn arn:aws:iam::972918601805:role/ctf-github-leak-role --role-session-name CTFTestSession --external-id githubShadow

This will provide an output like:

    "AccessKeyId": "...",
    "SecretAccessKey": "...",
    "SessionToken": "...."

Step 5: Authenticating with AWS

Export the credentials in your shell:

export AWS_ACCESS_KEY_ID=<access_key>
export AWS_SECRET_ACCESS_KEY=<secret_key>
export AWS_SESSION_TOKEN=<session_token>

Verify that the credentials work:

aws sts get-caller-identity

Expected output:

{
    "UserId": "...",
    "Account": "...",
    "Arn": "arn:aws:sts::872101052618:assumed-role/CTFReadOnlyS3/CTFSession"
}

Step 6: Discovering the S3 Bucket

Hints in the repository (issues, gists, or commit comments) mention "logs from the CI deployment" or "check app-startup logs." This points you toward the bucket name:

app-startup-logs

List the bucket to confirm access:

aws s3 ls s3://app-startup-logs/

Step 7: Retrieving the Flag

Now, download the flag:

aws s3 cp s3://app-startup-logs/flag.log .
cat flag.log

Output:

FLAG-{gefaCCUi31RFCcqNHFD5d8r3VgRVrv3r}

The purpose of the exercise is to demonstrate how sensitive data can persist even after deletion from Git history or repository forks.

The S3 bucket policy limits users to s3:ListBucket and s3:GetObject on a single resource, ensuring no write or privilege escalation is possible.
