CloudTrail Based AI Threat Detection

Published on January 2026

Cloud environments generate massive volumes of audit logs, yet most security incidents still go undetected until damage is done. While AWS provides managed detection services like GuardDuty, understanding how detections work — and building custom, explainable pipelines — is a critical skill for cloud security engineers.

In this project, I built an end-to-end AI-driven CloudTrail threat detection system that ingests AWS audit logs, models behavioral baselines, applies hybrid rule + ML scoring, and generates human-readable alerts.

Architecture Overview

  • AWS CloudTrail logs stored in S3
  • Local ingestion and normalization into structured parquet datasets
  • Behavior window aggregation (per identity, per time window)
  • Unsupervised anomaly detection using Isolation Forest
  • Rule-based risk weighting for high-impact IAM actions
  • Alerting via AWS SNS with contextual explanations
Design goal: Build explainable detections — not a black box.

Why Not Just Use AWS GuardDuty?

GuardDuty is an excellent managed service, but it intentionally operates as a black box. This project focuses on:

  • Transparent feature engineering
  • Customizable detection logic
  • Explainable alerts (“why did this fire?”)
  • Account-specific behavioral baselining

Many organizations run custom detections alongside GuardDuty to reduce false positives and detect organization-specific abuse patterns.

Feature Engineering & Behavior Modeling

Raw CloudTrail events are aggregated into fixed time windows per principal (IAM user or role). Each window is transformed into numerical features such as:

  • API call volume
  • Failed API ratio
  • Unique services accessed
  • Privilege-related API usage
  • MFA usage patterns

These features allow the model to learn normal behavior without requiring labeled attack data.

Machine Learning: Isolation Forest

I used an Isolation Forest for unsupervised anomaly detection. Unlike supervised models, it does not require pre-labeled malicious events, making it well-suited for cloud audit data.

Anomaly scores are normalized into a 0–100 range to allow consistent comparison across time windows.

Hybrid Rule + ML Scoring

Pure anomaly detection often flags benign spikes. To reduce false positives, I implemented a hybrid scoring engine that combines:

  • ML anomaly score
  • High-risk API usage (e.g. CreateAccessKey)
  • Identity context (IAM user vs assumed role)
  • Privilege indicators

This mirrors real-world detection engineering, where ML highlights anomalies and rules add security context.

Alerting & Explainability

Alerts are generated only when combined risk exceeds defined thresholds. Each alert includes:

  • Who: Identity involved
  • What: Suspicious behavior window
  • Why: Anomaly + rule-based reasons
  • Confidence: Final risk score

Alerts are delivered via AWS SNS and summarized in Markdown incident reports.

Attack Simulation & Validation

To validate the pipeline, I simulated IAM abuse scenarios such as:

  • Access key creation
  • Privilege escalation attempts
  • Unusual API usage bursts

These simulations produced clear spikes in anomaly scores, validating the detection logic end-to-end.

Key Takeaways

  • Cloud security detection is as much about context as ML
  • Explainability matters for incident response
  • Unsupervised models are powerful for audit logs
  • Defense-in-depth beats relying on a single service

Future Improvements

  • Streaming ingestion via Kinesis
  • Visualization dashboard (OpenSearch / Streamlit)
  • More granular IAM permission analysis
  • Automated incident enrichment

This project demonstrates practical detection engineering skills that translate directly to cloud security, DevSecOps, and security engineering roles.
